# Этап 2 — разработка

Задача: $ARGUMENTS (файл `tasks/$ARGUMENTS-*.md`; если номер не указан — последняя со статусом «утверждено»).

## 0. Проверка готовности
- Статус постановки должен быть «утверждено». Иначе — остановись и предложи `/task`.
- Если папка не git-репозиторий — `git init`. Сделай контрольную точку: `git add -A && git commit -m "checkpoint: перед задачей NNN"` (если есть что коммитить).
- Поставь статус «в работе». Заведи список подзадач в TodoWrite/задачах.

## 1. Разработка — по одной подзадаче
Для каждой подзадачи:
1. Напиши код по скиллу `frontend-developer`.
2. Напиши/обнови тесты в `tests/*.spec.js` (Playwright): каждый критерий приёмки, который можно проверить автоматически, — отдельный тест. Обязательно: основной сценарий, ошибки/пустые значения, мобильная ширина.
3. Запускай только тесты этой фичи: `npx playwright test tests/<файл>.spec.js`. Красное — чини код (не тесты, если тест верно отражает критерий). Запрещено ослаблять правила и удалять тесты.

**Экономия времени:** полный `npm run check` — ровно один раз перед ревью кода (после всех подзадач) и один раз в финале. Без повторных и «стресс»-прогонов; нестабильный тест разбирай точечно (только его, не весь набор).

## 2. Ревью кода — цикл до чистоты
1. Получи список изменённых файлов: `git status --porcelain` / `git diff --stat`.
2. Запусти **новый** сабагент `code-reviewer` (Agent, subagent_type: `code-reviewer`). В промпт передай ТОЛЬКО:
   - путь к постановке `tasks/NNN-*.md`;
   - список изменённых файлов;
   - номер раунда;
   - результат твоего последнего `npm run check` (одной строкой: зелёный/красный, сколько тестов).
   Не пересказывай ему свои решения и не объясняй код — ревьюер должен смотреть свежим взглядом.
3. Исправь все 🔴 и разумные 🟡. С чем не согласен — запиши причину для отчёта.
4. Прогони тесты затронутых файлов, затем `npm run check` → снова **новый** `code-reviewer`. Повторяй, пока 🔴 = 0.
5. Если после 3 раундов 🔴 остаются или ревьюер считает, что постановка противоречива, — остановись и спроси заказчика простыми словами.

## 3. Ревью UI — если в постановке «Есть UI: да»
Запускай **только после того, как ревью кода дало «ПРИНЯТО»**, и не параллельно с другими ревьюерами или прогонами тестов: одновременные прогоны мешают друг другу (общая папка `test-results/`, один сервер) и дают ложные падения.
1. Запусти сайт в фоне: `npm run serve` (http://localhost:4173), если ещё не запущен.
2. Запусти **новый** сабагент `ui-reviewer` с тем же минимальным контекстом (постановка + файлы + раунд). Он проверяет сайт в настоящем браузере через Playwright MCP: разные ширины, клики, формы, клавиатура, консоль.
3. Цикл как в п.2: исправить 🔴 → тесты затронутых файлов → новый `ui-reviewer`, пока 🔴 = 0.
4. Если Playwright MCP недоступен — скажи об этом в отчёте и проведи ревью по скриншотам `npm run screenshots`.

## 4. Финал
- Финальный `npm run check` — должен быть зелёным.
- Отметь критерии приёмки в постановке `[x]`, статус «готово».
- Запусти сайт для просмотра в фоне: `npm run serve` (http://localhost:4173) и открой его: `open http://localhost:4173`.

## 5. Отчёт заказчику (коротко, без жаргона)
```
## Готово: задача NNN — <название>

Что сделано:
- <подзадача> — <что теперь видит/может пользователь>

Проверки:
- Автотесты: N из N пройдено (из них новых: M)
- Ревью кода: K раунд(ов), критичных замечаний не осталось
- Ревью UI: K раунд(ов), проверено на телефоне, планшете, компьютере, в светлой и тёмной теме
- Не исправлено (некритично): <список или «нет»>

Посмотрите, пожалуйста: http://localhost:4173
Что проверить руками: <2–4 конкретных действия>

Если что-то не так — напишите, что поменять. Откатить задачу целиком тоже можно.
```
